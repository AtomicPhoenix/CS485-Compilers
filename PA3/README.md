# Design Decisions
## Generating TAC
We first parse through the input ".cl-type" file according to the specs for the different IRs contained within it. We then use the annotated AST to create TAC by going through each element in the IR and convering every method within it into TAC. In addition to the standard TAC elements (operand, arguments, and result), we also store the line number and static type of the expression being parsed for later use when generating assembly. 
### Scope Handling
In order to handle scope we used a hashtable to store in scope variable names. Before creating TAC for a method, we reset the hashtabl to ensure that we do not keep variable names from another scope (we make sure to add class attributes and method arguments back into scope before parsing methods). A variable name is added to the hashtable at any location where an assignment takes place, including let statements and case statements. We remove values from the table when they go out of scope (such as at the end of a let statement).
## Case Statements
For the most part, our TAC generation closely follows the reference compiler, however the compiler does not generate TAC for case statements. It does however, generate assembly for Cases statements, allowing us to work backword and mimic their implementation. We have a TAC operand specifically for a Case statement, which will later be converted into a check for type equality and subsequent jump to a case branch. We a Case Tac for every class in the class_map, with the jump label being determined by finding the least type of the defined case statement which the class matches, or empty (no matching case) if none.
## Assembly Generation
We create a CFG with TAC as its nodes, and use that as a basis for assembly generation. We convert each TAC statement into assembly, mostly following the reference compiler but adding our own optimizations wherever possible (Such as by calling a class's new method directly rather than putting it in a register first). We replace many of the standard helper functions generated by the reference compiler (such as the comparison handlers) with equivalents handwritten by ourselves or by creating a C file and then copying the assembly output of gcc on that file. We also take advantage of the c library whenever possible within our assembly output.
# Test Cases
## args.cl
This test-case tests the usage of methods with one to twelve arguments. This test case was extremely useful for making sure that we were correctly preserving register and stack values across method calls. At first it may seem as though going beyond the amount of arguments needed to preserve registers and then one more for the stack may seem excessive, but we did at certain points find stack misalignment errors only on 8+ args.
## void-comparison.cl
This test case does various comparison operations between void types and between void types and non-void types, ensuring that we are correctly handling such comparisons.
## special_characters.cl
This test case ensures that we are correctly handling the printing of special characters in our assembly code so as to ensure our compiler is correct in its handling of strings.
## divide-by-zero.cl
Ensures we correct trigger an error on divide by zero operation
