Handling of the class hierarchy:
    We handled the class hierarchy of COOL by effectively treating the AST as a dependency tree. Every class stores information about its parent, if it has any, and that information can be used to traverse up the class tree whenever needed, such as for subtyping and checking for the least upper bound of two classes.

Checking non-expressions (PA2c2):
    Our program iterates over the AST a few times to do multiple different checks. First of all, the program checks for a class cycle because it makes recursion easier if we can guarantee there will be no cycles in classes. After that, the method map is created, and all methods are verified. This includes things like verifying that methods have valid classes according to the class map, identifiers like 'self' or 'SELF_TYPE' are not used, and duplicate formal parameter names are prevented. After that, the AST is valided to check that there is a Main class with a Main function, and that every class inherits a valid class. Following that, attributes are checked by iterating over every class and checking the validity of each attribute individually, using a helper function to create a list of all attributes for a class including the attributes of the parent.

Checking expressions:
    To check expressions, the entire AST is iterated over again, and it recursively checks expressions uisng a function that also gets the type of the method so that its static type can be stored for printing later. This function is called 'get_type'. This function verifies things like operators have correct types, dispatch is handled properly, and other cases. The AST iteration distinguishes between attributes and methods, and is able to check the initializer of all attributes along with the bodies of all methods within the same AST iteration. Throughout the traversal, a map is maintained of all variables in the COOL program that is used to check identifiers to make sure they have been defined before use and are being used in valid situations.

Handling new expressions:
    Compared to other complex checks like dispatch and case, the new operator is relatively simple. The program checks if the identifier given for new is SELF_TYPE, and if so gives the expression the static type of the class the method was called under. Otherwise, the function simply verifies that the class given as an identifier is valid, and if so returns that class as the expression's static type.

Handling Case:
    Case is probably the second most complicated function that is handled in terms of code. To start off, the list of case elements is mutated into a list of the type names of each element, for easier use in verifying and laterjoining the types. After that, a recursive auxiliary function does the job of ensuring that every type in the type list is a unique type. Following that, the program creates a list of the static types for each case expression verifying that the expressions themselves are sound according the type system along the way. Finally, the function uses a 'lub' on all of the static types of the case to return the least upper bound of every possible case the function could give. The expression of the case is also checked to produce a valid type, but it is not compared to anything as that is not required by COOL.

Handling dispatch:
    Dispatch is one of the most complex parts of COOL, and this is reflected in typechecking. With 3 variants each having slightly different mechanics, it makes checking it difficult at times. For all dispatches, the first thing done is getting the method from the method map for the specific class, and verifying first that the amount of formals in the method's header is the same as the amount of arguments given by the call. The static dispatch also verifies that the method given is valid for the type given around this point. Afterwards, each argument has its type checked and noted down for validity and later printing, iterating over the list of arguments and formals to then check if the static type of the argument is a subtype of the formal parameter. Finally, the static type of the method is set to simply be the return type of the method. The checking of the method returnign the proper type is checked earlier in the typechecking process, so it can be assumed that the method will always return the correct type.
